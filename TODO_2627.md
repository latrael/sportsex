- [x] **R1.1** Typed FPL client: `bootstrap-static`, `fixtures`, `event/{gw}/live`. Retry with backoff, a real User-Agent, and raw response retention so any parse can be replayed without refetching.
      Lives in `apps/web/src/lib/fpl/`: `types.ts` (zod schemas), `parse.ts` (pure parsers + `parseByEndpoint` replay), `client.ts` (`FplClient`).
      Design decisions worth knowing:
      - **Fetching and parsing are separate.** Every parser takes plain `unknown`, so a payload archived today can be re-parsed by tomorrow's code with no network call. The client returns `{ data, raw }` and takes an `onRaw` hook — point it at a table or blob store in R1.5 and the whole backfill becomes replayable.
      - **Every schema is `.passthrough()`.** FPL adds fields mid-season without notice (`defensive_contribution` is a 25/26 arrival). Unknown fields must never fail a parse.
      - **Decimal fields stay strings** (`"expected_goals": "8.23"`), exactly as the wire carries them. Parsing them to JS numbers here would put a float in front of every Decimal column; Prisma takes the string directly. This is R2.4's rule applied one layer earlier.
      - Retry covers 408/425/429/5xx, transport errors, and truncated bodies (a half-received 2 MB payload is a transport problem, not a schema problem). Full-jitter exponential backoff, `Retry-After` honoured up to 60s and a hard fail beyond that. 4xx other than those listed fail immediately. `random`, `sleep` and `fetch` are all injectable, so backoff is asserted exactly and no test spends real seconds.

      Design decisions worth knowing:
      - **Identity and season membership are separate tables.** FPL renumbers every `element.id` and `team.id` in early August, so those ids are useless as keys — but they're also the *only* keys `fixtures` and `event/{gw}/live` carry. Splitting `fpl_player`/`club` (stable `code`) from `player_season`/`club_season` (season-scoped `fplId`) gives both: cross-season identity, and a `(seasonId, fplId)` mapping that still resolves a 25/26 payload after the rollover has reassigned those ids. Without it, replaying the backfill post-August (R1.7) would silently attribute stats to the wrong players. This is the main reason the table count is 6 and not 3.
      - **Planning is pure and separate from writing**, same split as R1.1's parse/fetch. `planBootstrap(payload)` → rows, no clock, no DB, no network. All 22 planner tests run against the checked-in fixture.
      - **Hard failures vs warnings is an operational choice, not a taste one.** Anything that would corrupt data or break a unique constraint (element pointing at an absent team, duplicate `code`/`opta_code`, a date in a format FPL has never used) throws and stops the ingest. Per-row noise a transfer window can produce (`team_code` disagreeing with `team`) comes back as a warning, because failing there would take the daily cron down for one inconsistent row.
      - **Writes are diffed, not upserted.** Prisma's `upsert` always issues an UPDATE, so a re-run would report ~900 writes with nothing changed and R1.7 could never be honestly satisfied. `applyDiff` (`src/lib/ingest/diff.ts`) reads first and writes only what moved, normalising `Date` and `Decimal` so Prisma's return types don't read as changes. Ingestion never deletes: FPL drops elements mid-season and their history stays valid.
      - `Position` is mapped from `element_types[].singular_name_short`, not from the numeric `element_type` id, which is FPL's to renumber.

- [x] **R1.4** `event/{gw}/live` → `player_fixture_stat`, using the `explain` block for per-fixture attribution (this is what makes double-gameweeks correct). Raw payload stored alongside parsed columns.
      Code in `apps/web/src/lib/ingest/live/` (`plan.ts` pure, `sync.ts` writes), tables in `prisma/migrations/20260723184819_r1_4_live_stats`.
      **The double-gameweek decision — two grains, no apportionment:**
      - `player_fixture_stat` is built **from `explain`**, which is the only per-fixture attribution FPL gives. It carries the point-scoring identifiers split per fixture (minutes, goals, assists, clean sheets, goals conceded, own goals, penalties saved/missed, cards, saves, bonus, defensive contribution) plus `totalPoints` = the sum of that fixture's `explain` points. A player with two fixtures in one gameweek gets two rows here. This is the accept criterion.
      - `player_gameweek_stat` holds the full `stats` block verbatim at gameweek grain — including the ~20 model inputs (`expected_goals`, `expected_assists`, `expected_goals_conceded`, `tackles`, `recoveries`, `clearances_blocks_interceptions`, `bps`, `starts`, `influence`/`creativity`/`threat`/`ict_index`) that FPL reports **only** as gameweek totals. On a double these stay a single combined number. **Nothing is apportioned** — the option to guess an xG split was rejected exactly as the task warned. R3.1 reads gameweek-grain xG and decides what to do with it; R2.3 recomputes season aggregates by summing the gameweek totals (a double's total already includes both fixtures, so no double-counting).
      - The counting stats deliberately live in **both** tables: per-fixture (from `explain`) and as the gameweek total (from `stats`). For a single-fixture gameweek they're equal; the two grains are what let R1.6's per-fixture scoreline reconciliation and R2.3's season recompute each read the grain they need. `explain` lists an identifier only when it fired, so absent ones are genuine zeros and the per-fixture columns default to 0. The **free cross-check** the note flagged is wired as a warning: Σ `explain` minutes per player must equal the `stats` gameweek total (holds for every element in both sample payloads).
      - Decimal fields stay strings to the DB boundary (R1.1's rule); Decimal columns are `(10,2)` for the ICT family, `(8,2)` for the xG family.

A `bodyHash` (sha256 of the body) short-circuits the write when a re-fetch pulls byte-identical data, so archiving stays idempotent (R1.7) even though the payload also carries volatile fetch metadata. Chose a table over blob storage: no blob infra is wired, payloads are a few hundred KB, and jsonb keeps replay a one-liner (`parseByEndpoint`). Storing raw is opt-in per sync call (pass `raw`).

## Phase 2 — Schema v2 + derived aggregates · 3–4 days

- [x] **R2.1** Author schema v2: reference (`season`, `club`, `player`, `gameweek`, `fixture`), events (`player_fixture_stat`), derived (`player_season_stat`, `fair_value`), market (`price_tick`, `trade`, `position`, `ledger_entry`), product (existing user/social tables, largely unchanged).
      *Reference half already exists.* Phase 1 had to write to real tables, so R1.2 landed `season`, `club`, `club_season`, `fpl_player`, `player_season`, `gameweek` (plus `fixture` in R1.3, and `player_fixture_stat`, `player_gameweek_stat`, `raw_payload` in R1.4). They sit alongside the v1 tables in the same `schema.prisma`; nothing joins across the two halves. What's left for R2.1 is the derived, market and product tables. *Note:* R1.4 landed a **second events table** — `player_gameweek_stat`, the gameweek-grain home for the ~20 model inputs FPL reports only as gameweek totals (xG/bps/tackles/ICT). R2.3 recomputes season aggregates by summing it (a double's total already includes both fixtures). R2.3 reads counting stats from `player_fixture_stat` and model inputs from `player_gameweek_stat`.
      **Accept:** met (`c6e3e7b`). Seven new v2 models in `schema.prisma`, schema `prisma validate`-clean and pushed onto the test DB by the suite's `db push --force-reset` (199/199 tests still green, typecheck clean, lint unchanged at 0 errors). No migration here — that is R2.2. Decisions worth knowing:
      - **The polymorphic pair is replaced by an `asset` table, not by more strings.** v1's `Holding`/`Transaction` carried an `assetKind` string + bare `assetId` with no foreign key (REBUILD_PLAN §"Positions have no referential integrity"). v2 introduces one `asset` row per tradeable instrument, and `position`/`trade`/`price_tick`/`fair_value` all carry a real FK to it. Player-vs-club is an **exclusive arc** on `asset`: `playerSeasonId`/`clubSeasonId` are both real FKs, exactly one is set, and an `AssetKind` discriminator makes position-group scans index-friendly. The XOR itself isn't expressible in Prisma, so R2.2's migration adds a raw `CHECK` — flagged there.
      - **Assets are season-scoped** (arc points at `player_season`/`club_season`, not the cross-season identity), because fair value is computed per season. What happens to an open position at the August rollover is a live product decision (R7.6), deliberately *not* frozen into the schema here.
      - **Money types land now, not deferred to R2.4.** Coins are `BigInt` minor units (`trade.grossCost`/`fee`, `ledger_entry.amount`), prices/fair values are `Decimal` (`price_tick.price`, `fair_value.value`, `position.avgCost`), share counts stay `Int`. Authoring these in R2.1 avoids a second migration; **R2.4 is now purely the code-path job** — no float coercion at the DB boundary.
